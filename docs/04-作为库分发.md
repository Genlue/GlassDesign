# 04 · 作为库分发

面向维护者：怎么把 `控件/` 发成一个能 `cargo add` 的 crate，以及发布之后哪些改动算破坏。

`host/`（`glass-design-host`）走同一套流程，只是它不上 crates.io 也无所谓——宿主胶水的复用价值低于界面库本身，发不发另说。

---

## 1. 发布前清单

一条一条过，缺哪条都会在别人机器上炸。

| # | 检查项 | 怎么查 |
|---|---|---|
| 1 | 元数据齐 | `控件/Cargo.toml` 有 `description` / `license` / `readme` / `repository` / `keywords` / `categories` / `rust-version`。`repository` 指向 `https://github.com/Genlue/GlassDesign`，crates.io 侧边栏与源码链接都读它 |
| 2 | `include` 白名单只带运行期资源 | `cargo package -p glass-design --list` 不含 `css/src/`、`target/`、`docs/` |
| 3 | 版本号与 `install()` 写出的 `VERSION` 一致 | 同源，不用查：`VERSION = env!("CARGO_PKG_VERSION")` |
| 4 | `CHANGELOG.md` 有对应条目 | 根目录 `CHANGELOG.md` 的 `## [0.8.0]` |
| 5 | 文档里的组件数与实测一致 | `grep -rho "#\[component\]" 控件/src \| wc -l`，减去非 `pub` 的 |
| 6 | 本地编译底线全绿 | `docs/03` §5.1 |
| 7 | 包体积没异常 | `docs/03` §5.2（< 120 文件 / 压缩 < 600 KiB） |
| 8 | 工作区干净 | `git status --short` 为空，否则 `cargo package` 会拒绝 |
| 9 | tag 名与版本一致 | `v0.8.0`，打 tag 在 `cargo publish` **之后** |

第 3 条值不值得单列：值得。`data-gd-version` 是截图里的证据链——如果 `Cargo.toml` 升了版而某个地方硬编码了版本号，页面上就会显示旧值，而 `cargo` 看不出来。目前只有一处来源，别引入第二处。

## 2. `cargo publish --dry-run`

```sh
cd 控件

# ① 打包不发布，看文件清单与体积
cargo package --list

# ② 真正打包（含一次编译验证）
cargo package

# ③ 走一遍发布流程但不推上去
cargo publish --dry-run

# ④ 上线
cargo publish
git tag v0.8.0 && git push --tags
```

- `--offline` 只对编译与打包有效，`cargo publish` 必须联网。本机走代理可以跑通：`https_proxy=http://127.0.0.1:7890 cargo publish --dry-run` 已实测到 `Uploading` 才退出。
- `cargo package` 会编译一次验证：这一步挂了说明 `include` 漏了文件（最常见的是 `css/glass.css` 或 `assets/glass-defs.svg`），本地 `cargo build` 是发现不了的——本地有这些文件，包里没有。
- `cargo publish --dry-run` 之后 crates.io 上什么都不会留，可以重复跑。
- 发布后**不能撤回**（只能 `yank`，`yank` 也只是让新解析不选它）。版本号一旦用掉就不能复用。

### 2.1 走 CI 发布（推荐）

`.github/workflows/release.yml` 已经接好：`workflow_dispatch` 手动触发，或 `v*` tag 触发。

1. crates.io → Account Settings → API Tokens，建一个 `publish-new` + `publish-update` 权限的 token。
2. 仓库 Settings → Secrets and variables → Actions，加 `CARGO_REGISTRY_TOKEN`。
3. Actions → Release → Run workflow。

工作流会先跑单测与 wasm 编译，再 `cargo publish`；缺 token 会在第一步明确失败，不会静默跳过。传上去的版本不可撤回，所以那两道关不能省。

### 2.2 发布包内容

```text
src/**                    Rust 源码（含 base / layout / widgets）
css/glass.css             展开后的单文件（331 KB）
assets/glass-defs.svg     预计算位移/高光贴图（134 KB）
examples/**               最小可运行示例
README.md
Cargo.toml / Cargo.lock / .cargo_vcs_info.json / Cargo.toml.orig   （cargo 自动加）
```

不含：`css/src/`（编辑源，64 个分区）、`docs/`、`scripts/`、`应用/`、`index.html`。少了 `css/src/` 就少了接近 1 MiB，这是包体积能压到 400 KiB 的主要原因。当前实测：84 个文件 / 1.3 MiB / 压缩 405.5 KiB。

## 3. semver 规则

| 改动 | 版本 |
|---|---|
| 新增 prop（带默认值）、新增组件、新增令牌、新增 feature | minor |
| 新增 `IconName` 常量、扩展枚举（**不破坏已有匹配**） | minor |
| 改 props 形状（改类型、必填化、改名） | major |
| 删组件、删 prop、删 `prelude` 导出 | major |
| 改 DOM 契约（类名、`data-*`、ARIA 角色） | major |
| 改键盘契约（方向键、Esc、Tab 顺序） | major |
| 改贴图尺寸档位（`CapsuleSize` 的像素值、`GlassPanelSize`） | major |
| 改 CSS 变量名 | **先加别名**，下个 major 再删 |
| 纯 CSS 观感调整（颜色微调、模糊强度） | patch |
| 修 bug、改文案 | patch |

“改 DOM 契约”为什么算 major：调用方会写 `.c-capsule[data-size="180"] { … }` 这类选择器做局部覆盖。类名与 `data-*` 一改，他们的覆盖就静默失效，页面不会报错，只是变样。这是最难查的一类破坏，所以按 major 处理。

CSS 变量先加别名：`--r-md` 改名为 `--radius-md` 时，同时写

```css
--radius-md: 12px;
--r-md: var(--radius-md);   /* 兼容旧名，下个 major 删掉这行 */
```

## 4. 0.x 的双版本共存风险

**这是 0.x 阶段最需要知道的一件事。**

cargo 的版本解析规则是：`0.8` 与 `0.9` 视为**不兼容的两个 crate**，可以同时出现在同一份依赖图里。于是：

```text
应用
├── glass-design 0.8.3     ← 直接依赖
└── some-widget-lib 1.2
    └── glass-design 0.9.0  ← 它自己声明的
```

两份 `glass-design` 同时被链接。两份的 `install()` 都会跑，而 `install()` 的去重是按 DOM id 做的：

```rust
if doc.get_element_by_id("gd-styles").is_none() { /* 注入 */ }
```

第一份注入后，第二份看到 `gd-styles` 已经存在，**直接跳过**。结果：页面用的是先挂载的那一版的样式，但组件可能是另一版的。新组件缺样式、新令牌没定义，表现为“看起来没坏，但就是不对”。

后果与做法：

| 现象 | 原因 | 做法 |
|---|---|---|
| 新组件显示成裸 HTML | 样式是旧版注入的，旧版没这个组件的规则 | 升级时**全图统一**：`cargo tree -i glass-design` 看清楚谁在拉旧版 |
| 令牌改了没生效 | `set_token` 写在新版那一份的 `Theme` 上，但 CSS 是旧版的 | 同上 |
| 组件数与文档不符 | 两份 `prelude` 都有导出，`cargo doc` 会互相盖 | 同上 |

**结论：尽快到 1.0。** 到 1.0 之后 `1.x` 内部的 patch / minor 共享同一份 crate，`install()` 的去重是正确行为；而 `0.x` 阶段的每个 minor 都是一个会被 cargo 当成“另一个库”的坐标，共存概率随生态增长线性上升。

在 1.0 之前能做的：

1. 在 README 里写清“整条依赖链必须同版本”。
2. `cargo tree -d glass-design` 加进 CI（可选，见下）。
3. 不发 `0.8` 与 `0.9` 两个还在维护的线，旧线只修安全问题。

```sh
# 检查图里是否有两份
cargo tree -d | grep -A3 glass-design
```

## 5. 破坏性变更清单模板

发 major 时把这张表填进 `CHANGELOG.md` 的 `### Breaking` 段，一条一行。写“什么变了 / 旧写法 / 新写法”三列，不要只写“重构了 X”。

```markdown
### Breaking

| 变了什么 | 旧写法 | 新写法 |
|---|---|---|
| `Capsule` 的 `size` 从 `u16` 改成 `CapsuleSize` | `size=180` | `size=CapsuleSize::Md` |
| 删除 `CardGroup` | `<CardGroup>…</CardGroup>` | `<Stack>…</Stack>` |
| `Toast` 默认时长 3.2s → 4.0s | — | 传 `duration` 保持旧值 |
| `.c-capsule[data-size]` 的取值从像素改成档位名 | `[data-size="180"]` | `[data-size="md"]` |

迁移脚本 / 批量替换：`sed -i 's/data-size="180"/data-size="md"/g' src/**/*.css`
```

三条自查：

- [ ] 每一条都能回答“调用方怎么知道自己被影响了”——靠编译错误，还是靠肉眼？
- [ ] 靠肉眼的那几条，有没有写进迁移说明？
- [ ] 有没有可能用“加别名 / 加默认值 / 加新组件”变成 minor？能降级就降级，major 的成本在别人身上。
